ORDERSOFT - REFERENCIA TECNICA Y BITACORA DE MANTENIMIENTO
==========================================================
Documento de referencia no ejecutable.
Objetivo: concentrar notas tecnicas, estructura, procedimientos, comprobaciones y plantillas de mantenimiento del proyecto OrderSoft.
Este archivo no debe importarse desde el backend ni desde el frontend y no modifica el comportamiento de la aplicacion.
Fecha de preparacion: 2026-08-11
----------------------------------------------------------------
1. CONTEXTO GENERAL
----------------------------------------------------------------
OrderSoft es un proyecto dividido en dos componentes principales:
- backend
- frontend
De acuerdo con la estructura revisada, el backend utiliza Node.js y TypeScript.
El frontend corresponde a una aplicacion Flutter/Dart.
El repositorio incluye configuracion para una base de datos y archivos de migracion.
Archivos y carpetas observados en el backend:
- src/
- node_modules/
- docker-compose.yml
- package.json
- package-lock.json
- schema.sql
- run_migration.js
- run_migration_pnj.js
- tsconfig.json
- .gitignore
Dependencias observadas en package.json del backend:
- bcryptjs
- cors
- dotenv
- express
- jsonwebtoken
- pg
Dependencias de desarrollo observadas:
- @types/bcryptjs
- @types/cors
- @types/express
- @types/jsonwebtoken
- @types/node
- @types/pg
- tsx
- typescript
Scripts observados en package.json:
- npm run dev  -> tsx watch src/app.ts
- npm run build -> tsc
- npm start -> node --enable-source-maps dist/app.js
----------------------------------------------------------------
2. PRINCIPIOS PARA TRABAJAR CON EL REPOSITORIO
----------------------------------------------------------------
Antes de comenzar una sesion de trabajo:
1. Abrir la copia del proyecto que contiene la carpeta .git.
2. Confirmar la rama actual.
3. Descargar cambios recientes.
4. Verificar que no existan modificaciones locales inesperadas.
Comandos de referencia:
git status
git branch
git pull origin main
Al terminar una sesion:
git status
git add .
git commit -m "descripcion clara del cambio"
git push origin main
Regla de mantenimiento:
- No editar archivos generados cuando exista una fuente original equivalente.
- No subir credenciales ni secretos.
- No modificar dependencias sin documentar el motivo.
- No hacer cambios funcionales sin una prueba minima de ejecucion.
----------------------------------------------------------------
3. EJECUCION LOCAL DEL BACKEND
----------------------------------------------------------------
Ruta esperada de trabajo: carpeta backend.
Procedimiento base:
1. Abrir una terminal.
2. Entrar a backend.
3. Verificar package.json.
4. Instalar dependencias si hace falta.
5. Levantar servicios de infraestructura.
6. Ejecutar el servidor en modo desarrollo.
Comandos:
cd backend
npm install
docker compose up -d
docker compose ps
npm run dev
Para compilar TypeScript:
npm run build
Para iniciar la salida compilada:
npm start
----------------------------------------------------------------
4. EJECUCION LOCAL DEL FRONTEND
----------------------------------------------------------------
El frontend corresponde a Flutter.
Antes de ejecutarlo se recomienda verificar la instalacion de Flutter y los dispositivos disponibles.
Comandos de referencia:
flutter doctor
flutter pub get
flutter devices
Ejemplos de ejecucion:
flutter run -d windows
flutter run -d chrome
Nota:
El dispositivo exacto depende de los targets habilitados en el equipo.
----------------------------------------------------------------
5. CONTROL DE VERSIONES
----------------------------------------------------------------
Conceptos basicos:
- working tree: archivos actuales del proyecto.
- staging area: cambios seleccionados con git add.
- commit: registro local de un conjunto de cambios.
- remote: repositorio remoto.
- origin: nombre habitual del remoto principal.
- main: rama principal observada durante el trabajo.
Comprobaciones utiles:
git status
git log --oneline -10
git remote -v
git diff
git diff --staged
Para descargar cambios:
git pull origin main
Para subir cambios:
git push origin main

docker compose down

7. SEGURIDAD Y CONFIGURACION
----------------------------------------------------------------
Dependencias como bcryptjs y jsonwebtoken indican que el backend contempla autenticacion o manejo de credenciales/tokens.
Buenas practicas:
- Nunca guardar contraseñas en texto plano.
- Nunca incluir claves privadas en el repositorio.
- Mantener .env fuera de commits cuando contenga secretos.
- Revisar .gitignore antes de subir cambios.
- Rotar credenciales expuestas.
- Limitar informacion sensible en logs.

9. GUIA DE DIAGNOSTICO
----------------------------------------------------------------
CASO: fatal: not a git repository
  1. Confirmar la carpeta actual con Get-Location.
  2. Buscar una carpeta .git en el directorio o sus padres.
  3. Si el proyecto fue descargado como ZIP, clonar el repositorio en una carpeta nueva.
  4. Evitar ejecutar git init sobre una copia que debe conservar el historial remoto.
CASO: destination path already exists
  1. La carpeta indicada para git clone ya existe.
  2. Entrar a esa carpeta si ya contiene el clon correcto.
  3. Usar git status para verificar.
  4. No volver a clonar innecesariamente.
CASO: Everything up-to-date
  1. No hay commits locales pendientes de enviar.
  2. Revisar git log si se esperaba un cambio nuevo.
  3. Confirmar que se esta usando la rama correcta.
CASO: Already up to date
  1. El repositorio local ya contiene la ultima version del remoto.
  2. No es necesario volver a clonar.
CASO: Docker no inicia
  1. Abrir Docker Desktop.
  2. Esperar a que el motor este listo.
  3. Ejecutar docker version.
  4. Ejecutar docker compose ps.
CASO: Flutter no detecta dispositivo
  1. Ejecutar flutter devices.
  2. Confirmar que Windows/Chrome/Android esten configurados.
  3. Ejecutar flutter doctor y revisar advertencias.

17. NOTAS DE MANTENIMIENTO
----------------------------------------------------------------
1. Trabajar siempre sobre una copia clonada con Git.
2. Descargar cambios antes de comenzar.
3. Evitar modificar simultaneamente el mismo archivo entre integrantes.
4. Revisar git status antes y despues de cada cambio.
5. Probar backend y frontend cuando el cambio pueda afectarlos.
6. Mantener el repositorio libre de secretos.
7. Documentar cambios de configuracion.
8. Evitar commits gigantes sin motivo.
9. Mantener mensajes de commit descriptivos.
10. No usar archivos de documentacion como sustituto de pruebas reales.
